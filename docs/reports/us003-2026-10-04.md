## Setup

- **Model:** `ollama/gpt-oss:20b` on the local GPU, `num_ctx = 16384`.
- **Router:** `offline = true`, with a remote candidate (`remote/big-model`, `https://remote.invalid/v1`) listed
  first in the `code` and `fast` classes. REQ-LLM-004 must discard it without contacting it.
- **Each run:**
  - a fresh copy of `e2e/us003/fixture` under git;
  - `go test ./...` typed in a new pane, failing;
  - an `auto-edit` thread in the copy, sent `fix it` with that block attached;
  - `run_command` approved once when the line is a single `go test`, anything else asked about denied;
  - the verdict from running `go test -count=1 ./...` again outside the daemon.
- **Success:** `go test ./...` green, `stats_test.go` unchanged, and git reporting no path changed but
  `stats.go`. A run that edits the test, adds a file or touches `go.mod` fails.
- **Offline:** the panes and the agent run with `GOTOOLCHAIN=local`, `GOPROXY=off` and `GOFLAGS=-mod=mod`.
- **Environment:** the daemon has its own XDG directories and `HOME`; the Go build and module caches are
  the developer's, which keeps a run's builds warm. Ollama keeps the model loaded (`keep_alive = "30m"`).
- **Measures:** "left after repair" counts the turns REQ-AGT-006 ended `tool_error` on an invalid
  retry — one unrepaired call each — over every tool call, which is how PRD §4.1 reads "the rate of invalid
  tool calls after repair". "Repairs that failed" puts the same count over the invalid calls. An invalid
  call whose turn ended for another reason before its retry is not counted. One model is measured.

## Analysis

*Written by hand after the run; everything else in this report is generated by the harness.*

- **Targets.**
  - 16 of 20 runs ended green (80 %). That is above PRD §4.1's 70 % and T-F1-21's 14/20. In
    each green run `stats_test.go` was untouched and git reported only `stats.go` changed.
  - `egress_log` was empty, and so were the `usage` rows for the remote candidate listed first
    in both classes. REQ-LLM-004 discarded it without a single request, and nothing left the
    machine (REQ-SEC-002, Art. 4).
- **The repair message was unreadable before this task.** The first pass of the day scored
  15/20, with 19 of 128 calls invalid (`us003-2026-10-04-before-repair-fix.md`, from an earlier
  revision of the harness).
  - The schema's error reached the model as a printed Go value: `list_dir: /: &{[depth]}`.
  - The model resent the same property, and two turns ended `tool_error`.
  - The registry now sends the validator's English text, `additional properties 'depth' not
    allowed` (`TestTheRepairNamesWhatIsWrong_REQ_AGT_006`).
  - A second pass with the fix scored 17/20, under the earlier harness rules. This final pass,
    with the stricter rules, scored 16/20.
  - In this pass, 12 of 13 invalid calls were repaired on the next step.
- **What the model gets wrong.** Most invalid calls are a property the tool does not take: 8 of
  the 13 are `list_dir` with a `depth`, 2 have a `pattern`, and one is a call to an unknown
  `search` tool. The other two are `edit_file` calls in run 1 that tried to rewrite the whole
  function without an `old_string`: one left it out, the other sent it empty.

  `list_dir`'s schema has no `depth`, and that is a choice the daemon made. Giving it one would
  lower the rate before repair (6.4 %). It changes a built-in's schema (REQ-AGT-002), so it is
  left for a delta of its own. After repair the rate is 1 of 203 (0.5 %). PRD §4.1's target
  is < 5 %, measured for this one model.
- **The four failures, and run 1.**
  - **Runs 11 and 14, `run_timeout`.** The model looped for ten minutes on `read_file` and
    `edit_file` pairs, 25-26 calls, without the fix landing. The harness cancelled them.
  - **Run 6, `provider_error`.** Same loop. It ended when Ollama returned `HTTP 500: error
    parsing tool call`: gpt-oss wrote prose where a tool call's arguments belong ("Our attempts
    to edit failed…").
  - **Run 15, `tool_error`.** `list_dir` with `depth` twice; the one repair did not take.
  - **Run 1** counts as green but is not clean. The fix was in place, so `go test` passed, but
    the turn went on editing until the 10-minute cancel.

  These loops are the largest source of lost time. The p90 latency of 9m59s is the three
  cancelled runs. They were all `edit_file` calls that did not apply, read back and tried
  again. This harness does not record why an edit failed: failed calls carry no result text.
  Recording it is the next thing to measure, before any prompt change.
- **Latency.** p50 1m37s from send to the turn's end, on gpt-oss:20b with a 16k context, for a
  three-file repository.
- **What is shared with the machine.** The Go build and module caches are the developer's; the
  daemon's XDG directories, `HOME`, socket and database are its own.
