# CHECKPOINT — T-F0-06, subscription, snapshot and fan-out

> 2026-09-11 · branch `feat/T-F0-06-subscribe-fanout` · output now reaches clients.

## The decision that mattered

API Spec §8 says output is "batched every 4 ms or 32 KiB, whichever comes first". Read as a
target, that means every chunk waits for a batch to fill. Measured, it puts the daemon's
added latency at **p95 4.24 ms** against REQ-TERM-006's **5 ms** budget, leaving almost
nothing for the rest of the path.

Read as a ceiling, the writer sends at once and coalesces only what piles up behind it while
a write is in flight. Measured after the change: **p95 12 µs**, 340 times better, and
batching still happens exactly when it is needed, because under load the writer is the slow
part.

| Strategy | p50 | p95 | max |
|---|---|---|---|
| Fixed 4 ms batch window | 4.15 ms | 4.24 ms | 4.55 ms |
| Send at once, coalesce under load | 8 µs | 12 µs | 81 µs |

`TestNoChunkWaitsLongerThanTheBatchInterval` keeps the ceiling honest: it fails if anyone
reintroduces a fixed wait.

## Ordering, and a test that did not work

`session.subscribe` registers the subscription **before** taking the snapshot. Output
arriving in between is then queued, and the snapshot's sequence number discards whatever it
already contains. Reversed, that window loses output with nothing to notice the loss.

The first version of the test did not catch it. The fake published output after subscribe
returned, so the window was never exercised. Publishing *inside* the snapshot call still did
not bite reliably, because whether the dispatch goroutine ran in the window was up to the
scheduler. It now asserts the ordering where it happens: a subscription must exist at the
moment the snapshot is taken. That fails deterministically when the order is reversed.

Worth recording because the first two versions looked like passing tests.

## Honest status

- **`changes/2026-09-slow-client-notification/` is a draft awaiting approval.** The daemon
  emits `session.unsubscribed`, which §6 does not list. Without it a dropped client sees
  output stop, which is indistinguishable from a quiet session. Until the delta is folded,
  the code and the spec disagree on that one notification.
- **The 8 MiB drop path has never run against a real slow client.** `TestSlowClientIsDropped`
  drives the subscription directly rather than through a socket, because filling 8 MiB
  through a real connection makes a slow test. The accounting is covered; the socket-level
  behaviour when a client genuinely stops reading is not.
- **`scrollback_lines` is validated and then ignored.** The snapshot always carries whatever
  the emulator holds, capped at 10,000 lines by the terminal's own budget. A client asking
  for fewer gets more. Narrowing it needs a formatter selection, which is T-F0-12's problem
  when the TUI decides what it wants.
- Control notifications still go to every authenticated connection; only output is
  restricted to subscribers. §6 does not say control events are per-session, so this is
  defensible, but it is worth revisiting when there are many sessions.
- The dispatch goroutine has a 2048-event buffer. A drop there is output no client will
  ever see. It is logged on shutdown only, not per event.
- Still no blocks: T-F0-09. macOS untested, and CI has never run on real GitHub.
