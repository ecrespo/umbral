> 2026-09-11 · branch `feat/T-F0-01-scaffolding` · reviewed by `spec-guardian` before the commit.

## The review changed the outcome

The first implementation passed every gate and was still wrong. `spec-guardian` returned
**FIX FIRST** with one CRITICAL and five HIGH findings. This is the entry worth reading:

| Finding | What it was | Reproduced? |
|---|---|---|
| CRITICAL | A token file that existed but was empty kept its old permissions. `os.WriteFile` does not apply its mode argument to an existing file, so the token landed at 0664 instead of 0600 | Yes, with a throwaway probe test: `token mode = 0664` |
| HIGH | The handshake validated `client_kind` before the token, so a bad token plus an invalid kind answered `VALIDATION_ERROR` and left the connection **open**, against REQ-SEC-003 | Yes, now covered by a test |
| HIGH | The runtime-directory fallback wrote the token into a world-writable parent without checking the directory's owner or mode | Read |
| HIGH | `trace_id` carried a freshly minted ULID that correlated to nothing | Read |
| HIGH | `capabilities` advertised `sessions` and `blocks` while no such method was registered | Read |
| HIGH | The task was not closed in `specs/`: no `[x]`, no Result line, no execution-log row | Read |

All are fixed. Five decisions the API Spec does not cover went into
`changes/2026-09-api-f0-decisions/` rather than staying in code comments.
