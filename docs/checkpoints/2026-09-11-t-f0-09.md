The pipeline is: the drain goroutine publishes a chunk to the bus, then feeds the same bytes
to the scanner; the scanner splits them into ordinary output and markers; the recorder turns
markers into `Action`s; the service carries the actions out against SQLite and the bus.

## Where the OSC parser is, and why it is not where the task file said

The task file asked for "OSC parser (emulator callbacks)". There are no such callbacks to
use. libghostty parses OSC, but its Go bindings expose the semantic-prompt command only as a
type with no payload accessor, and OSC 633 not at all, so neither the command line nor the
exit code can be read from the emulator. The scanner is therefore ours, and it lives beside
the bootstrap scripts because the two are halves of one protocol: a change to what a script
emits is a change to what the scanner reads.

The emulator still receives every byte unchanged. Only the block's stored output has the
markers removed, which VT-20 in the conformance suite had already shown to be invisible on
screen anyway.

## Three defects found by running real shells

**Every command was recorded as exit 0.** The bash and zsh bootstraps read `$?` in a hook
registered last, so that the prompt markers would survive a framework rewriting the prompt.
But each element of `PROMPT_COMMAND`, and each entry of zsh's `precmd_functions`, leaves `$?`
set to its own result: with Starship installed, the shell's own hook had already replaced the
command's exit code before ours looked. The work is now split in two, because its halves want
opposite positions: a capture hook first, the marker hook last. This shipped as part of
T-F0-08 and was wrong the whole time; nothing in T-F0-08 asked a shell for a non-zero exit
code.

**The daemon never answered terminal queries.** libghostty produces replies to Primary Device
Attributes, XTGETTCAP and the rest, and hands them to a write-pty effect that was never
wired, so they went nowhere. fish waits two seconds for its DA reply, prints a warning and
permanently disables features; under a test that retried a probe every 500 ms it never got
two quiet seconds and hung until the deadline. `ports.EmulatorFactory` now takes a
`ReplyFunc`, and the service routes it to the PTY. It bypasses the input lock on purpose:
REQ-TERM-008 is about people typing, and this is the terminal answering.

**Carriage return ate every line.** The plain-text stripper treated `\r` as "the line is
about to be overwritten", which is right for a progress bar and wrong for the CRLF a PTY ends
every line with. The decision is now deferred by one byte: `\r\n` is a line ending, `\r`
followed by anything else erases.

## Tests and how they were checked

`TestScanner…` (7 cases) and the recorder suite were each verified by breaking what they
guard, three properties and four respectively: dropping the carried prefix of a sequence
split across chunks, treating every private mode as the alternate screen, defaulting an
unknown exit code to zero, recording alternate-screen output, guessing an exit code for a
superseded block, never truncating at the raw cap, and counting any event as shell
integration. All seven failed as intended.

The matrix names are used where the matrix has one: `TestBlockStartsOnOSC133C_REQ_BLK_001`,
`TestBlockClosedOnOSC133D_REQ_BLK_002`, `TestIntegrationNoneAfter5s_REQ_BLK_003`,
`TestAltScreenMarksInteractive_REQ_BLK_004`, `TestPlainOutputHasNoEscapes_REQ_BLK_007`.

`TestBlocksInEveryShell_REQ_BLK_005` runs the same cycle under all three shells. It is the
test that found both of the defects above. Note for anyone extending it: `(exit 3)` is a
subshell in bash and zsh and command substitution in fish, where it ends the session, so the
exit code comes from an external `sh -c`.

## What the spec-guardian review changed

The review returned **NEEDS A DELTA**: no CRITICAL, one HIGH, nine lower findings. Seven were
acted on here.

Fixed in code, each with a test that was verified to fail without the fix:

- **The alternate-screen mode pair was unbalanced.** The enter sequence was suppressed and
  the leave sequence stored, so replaying a block's chunks began by switching the reader's
  terminal *out* of a screen it had never entered. The enter marker is now emitted before its
  own bytes and the leave marker after, so the `interactive` guard swallows both.
- **The plain-text line was unbounded.** The 1 MiB cap was applied when a line was committed,
  which never happens for output with no newline in it: a minified file, a one-line JSON
  dump, a base64 blob. The line itself is now capped.
- **Two of three block events were published even when their write had failed.** Only
  `block.started` returned early. DD-007's promise now holds for all three.
- **A session marked `integration: none` could never be promoted** while its blocks were
  being recorded, so `session.get` and `block.list` disagreed about the same session. A late
  marker now promotes it, and the reverse is forbidden.
- **A transcript cut at the 1 MiB cap left `output_truncated` false**, misleading the one
  consumer the flag exists for.
- `ports.BlockStore`'s doc claimed a shutdown timeout the context does not carry. It now says
  what is true.
- `blockstore` had no tests of its own. It has three, including a byte-for-byte chunk round
  trip and a check that the compressed form is smaller than the input.

Sent to `changes/2026-09-block-lifecycle-decisions/` rather than fixed, because they are
spec changes and not bugs: what `abandoned` means when a block is superseded, which sequences
`block_chunks` keeps, what `output_truncated` covers, the late-marker promotion, and
recording the zstd dependency in Tech Design §3.2. **That delta is a draft awaiting
approval.** The code implements what it proposes.

Left as noted: the 16 MiB cap is still never exercised at scale.

## Deliberately not done

- **`block.list`, `block.get` and `block.search`** are T-F0-10. Nothing reads these rows back
  yet except the tests.
- **Agent blocks.** `origin` and `thread_id` exist and the schema's CHECK enforces their
  relationship, but only `user` blocks are ever created. `run_command` is T-F1-10.
- **Chunk writes are on the drain goroutine**, after the chunk has been published, so they
  delay the stored history and never the live screen. Output is buffered to 64 KiB before a
  chunk is written, which also gives zstd a longer window than a 32 KiB PTY read would.
- **A block that outlives a daemon restart** is repaired by `store.Recover`, which was
  written in T-F0-02 and is not re-verified here.
- **The 16 MiB cap is enforced but not measured at scale.** The unit test writes just past
  the boundary; no test stores 16 MiB.
