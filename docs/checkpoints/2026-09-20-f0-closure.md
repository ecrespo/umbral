## The three things this found

**1. The test suite was writing to the developer's real database.**
`cmd/umbrald/bootstrap_test.go` overrode `XDG_RUNTIME_DIR` and nothing else, so the daemon it
started inherited the real `XDG_DATA_HOME` and opened `~/.local/share/umbral/umbral.db`. That
database now holds **28 workspaces, 2484 tabs, 2491 panes and 2490 sessions**, every one of
them created by a test, in 1.9 MB plus a 4.2 MB WAL. CI never showed it because a runner's
home is thrown away.

**2. The same test leaked a daemon per run.** `umbrald` outlives its clients by design
(REQ-TERM-003) and there is no `system.shutdown`, so closing both connections stopped nothing.
Four were found alive on this machine, the oldest 56 minutes old, each holding that database
open. Fixed: the test now owns the process and stops it, and `XDG_DATA_HOME` and
`XDG_CONFIG_HOME` are redirected. Verified — the test passes and leaves `0` daemons behind,
and the real database's mtime does not move.

**3. 2515 bootstrap directories in `/tmp`, 168 MB.** One `umbral-shellinteg-*` per session, each
holding the generated rc file. This one turned out **not** to be a production defect, and the
measurement is worth recording because the obvious reading is wrong. `Service.Shutdown` closes
each PTY without running the bootstrap's cleanup, which looks like a leak per live session per
shutdown — so a fix was written for it. Driving the real daemon both ways says otherwise: a
clean `SIGTERM` with two live sessions leaks **0** directories, because closing the PTY makes
the shell exit and the drain goroutine's exit handler runs the cleanup in time. `kill -9` with
two live sessions leaks **2**, and nothing can be run on `SIGKILL` by definition. The 2515 were
the residue of killed daemons and interrupted `go test` runs, defect 2 among them. **The fix
was reverted**: it changed no measurable behaviour and its comment asserted something the
experiment contradicts.

They do matter, though — a crash loop accumulates them and nothing ever removes them — so the
sweeper was specified rather than added quietly: delta `2026-09-bootstrap-sweeper`,
REQ-TERM-012, implemented by **`T-F0-19`**, which is not written. The design puts a shell's
bootstrap files in the daemon's own runtime directory and sweeps that directory at start while
holding the instance lock. The lock is the whole argument: `flock` on `umbrald.lock`, taken
before the database, dropped by the kernel however the holder dies — so a daemon that holds it
is the only one of its installation, everything under that directory belongs to a process that
is gone, and no age heuristic is needed. Sweeping the shared `/tmp` instead would race another
installation's daemon starting a session at that moment.

It is F0 rather than hardening because the code is F0's (the bootstrap is T-F0-08's, the
sessions that own it T-F0-05's), the phase is already open on two criteria, and hardening runs
after F1 — a long time to ship a path that grows without bound after every crash.

### Gap 1 — there is no CLI for the workspace tree

`umb` serves `status`, `block last`, `api schema`, `version` and `help`. There is no
`umb workspace`, `umb tab`, `umb pane` or `umb layout`. So criterion 4 cannot be performed at
all, and the daemon's addressing surface is reachable only over raw JSON-RPC.

This is not an oversight in a task — **no task covers it and no REQ requires it.** The only
place in the whole specification package that names the feature is the constitution's own
Art. 6 rationale:

> *it is typeable, because the command line is this design's addressing surface — `umb pane
> split w1:t1` is the feature, and the same command with a 26-character ULID is that feature
> with its usability removed.*

The Art. 6 amendment of 2026-09-20 justifies breaking the ULID rule for `w<n>`/`w<n>:t<m>`/
`w<n>:p<m>` on the strength of a command line that was never built. That is a gap between the
constitution and the backlog, so **it wants a Delta, not a quiet new task.** It is recorded
here and left for the next session to raise.
