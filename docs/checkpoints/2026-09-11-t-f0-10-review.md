## Still open, in the order to take them

**#3 HIGH — `output_raw_truncated` and the 2 MiB raw cap are wire contract that no spec
states.** API §5.11 says the result is "`Block` plus `output_plain` or `output_raw_b64`",
nothing else, and §8 has no raw-output cap. The decision lives in a code comment, which is
where Art. 9 says it must not live. Needs a delta adding the field to §5.11 and the cap to §8.
Additive, so `protocol_version` stays 1.

**#4 HIGH — the folded spec text went beyond what the delta proposed.** API §5.12 gained a
normative *"A client offering a search box SHALL quote what the user typed"* and §3 gained the
cross-method cursor rule; neither was in the delta's MODIFIED list or its Impact table. Decide
whether the quoting rule is a client requirement, in which case it needs a REQ, or a note, in
which case it should not be a SHALL. Either way the delta record has to match what was folded.

**#5 HIGH — `capabilities` name drift.** API §2 enumerates the namespaces as `sessions`,
`blocks`, `threads`, `mcp`, `models` and its example shows plurals, but the daemon derives them
from the method prefixes and emits `session`, `block`, `thread`, `mcp`, `model`. A client
branching on `capabilities.includes("blocks")` takes the wrong path. The same paragraph
requires the list to be *derived* from the method table, so the enumeration is the error: fix
§2 and its example through a delta rather than mapping in code.

**#6 MEDIUM — the advertisement can promise a namespace that cannot work.** `capabilities()`
reads the method table, and the `block.*` and `session.*` entries are registered whether or not
their port is wired; with a nil port they answer `METHOD_NOT_FOUND`. API §2 forbids exactly
this. Fix by registering those entries only when the port is non-nil, so the advertisement and
the dispatch agree by construction rather than by care.

**#7 MEDIUM — REQ-BLK-006's only guard runs in no gate.** `task bench` is not part of
`task ci`, and T-F0-13, the performance job, cites only REQ-TERM-001 and REQ-TERM-006. Add
REQ-BLK-006 and `BenchmarkBlockSearch100k_REQ_BLK_006` to T-F0-13's What, REQ and Files.

**#8 MEDIUM — `searchError` classifies by substring of the driver's message.** A wording change
in `modernc.org/sqlite` would silently turn every malformed query into `INTERNAL_ERROR` with a
trace id. Prefer the driver's error code. Four syntax shapes are pinned in the test, which
limits the damage but does not remove the fragility.

**#10 MEDIUM — the benchmark measures the wrong layer.** REQ-BLK-006 says "WHEN a client
invokes `block.search`", and the benchmark calls the store directly: the decode, the handler,
marshalling fifty blocks with snippets and the socket write are all outside it. The 0.93 ms
against a 200 ms budget makes it immaterial today. Either say so in the T-F0-10 Result or move
the measurement to the wire when T-F0-13 builds the job.

**#14 LOW — the §2.4 rowid note is incomplete.** It covers `VACUUM` but not deletion: SQLite
reuses the largest rowid once the newest row is gone, so the retention job of T-F1-22 can make
`ORDER BY blocks_fts.rowid DESC` put a later block before an earlier one. That is the exact
assumption `block.search`'s ordering rests on. Extend the note, or state the guarantee as
"insertion order, which retention must preserve".

**#15 LOW — `blocks.duration_ms` is written and never read.** `blockColumns` omits it and the
wire recomputes it from the timestamps. Consistent today; the column can drift from what the
API reports. Either select it or record in §2.2 that it is denormalised.

## One more thing T-F0-11 will hit immediately

REQ-CLI-002 says `umb block last` prints "the last closed block of **the current session**",
but nothing tells `umb` which session it is in. The daemon injects `UMBRAL_SESSION=1` into every
session's environment (`internal/sessions/lifecycle.go`) and no session id. No spec mentions
either variable. Carrying `UMBRAL_SESSION_ID` is the obvious mechanism and needs a delta,
because the requirement cannot be met without a documented contract between the daemon and its
CLI. It also needs the session id to be minted before the PTY is created, which today happens
after.
