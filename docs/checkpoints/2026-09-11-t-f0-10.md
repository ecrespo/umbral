## The requirement was missed on the first measurement

REQ-BLK-006 budgets 200 ms p95 for a search over 100,000 blocks. The first run:

| Query | p95, before | p95, after |
|---|---|---|
| `block.search` | 1226 ms | **0.93 ms** |
| `block.list`, one page of 50 | 129 ms | **0.22 ms** |

`EXPLAIN QUERY PLAN` named both causes and neither was the search itself.

**`blocks` had no index on the ordering it is listed by.** The three indexes in migration
0001 are all prefixed by `session_id`, `thread_id` or `state`, so an unfiltered page, which
is what the history pane and `umb block list` ask for, scanned and sorted the whole table.

**Ordering a full-text search by `started_at` sorts the whole match set.** A term matching
half the history put fifty thousand rows through a temporary B-tree to return fifty. No index
fixes it: rows arrive from the full-text index in rowid order and have to be re-sorted
whatever exists. Ordering by that rowid instead lets SQLite walk the index backwards and stop
at the limit, which is the 300-fold difference. The two orderings agree because a block's row
is written when its command starts, so insertion order is start order by construction.

Both changes needed spec text. The delta was approved and folded the same day into Data Model
v1.3 (`idx_blocks_started`, and the `VACUUM` rule below) and API Spec v1.4 (§3 names the
exception, §5.12 states the ordering).

## Two things worth knowing that the specs did not say

**FTS5 rejects a bare path.** `internal/sessions` is a syntax error in that grammar, because
an unquoted slash is not a bareword character. A client with a search box has to quote what
the user typed, or accept that paths fail. API Spec §5.12 says the query is FTS5, so passing
it through unchanged is what the contract asks for, but a client author will not expect this.

**`blocks_fts` depends on rowids that `VACUUM` may renumber.** It is an external-content
table keyed on `blocks.rowid`, and `blocks` has a `TEXT` primary key, so those rowids are
implicit and SQLite is free to reassign them. A `VACUUM` would desynchronise every row of the
index from the block it describes, and search would return the wrong blocks rather than fail.
This was already true before this task; ordering by rowid only made the dependency visible.
Data Model §2.4 now carries the rule: rebuild the index after any `VACUUM`.

## Tests

`TestBlockGetLast_REQ_CLI_002` exists twice, and not by accident. The requirement has two
halves, that the reserved id resolves to the right block and that the result follows the API
`Block` schema, and no package may see both: `internal/api` may not import the store, and
`internal/sessions/integration` may not import the wire. So the resolution is tested against
a real bash session and the schema against the handler, and the traceability matrix points at
the pair.

Six properties were checked by breaking them: `last` returning a block still running, paging
on the timestamp without its tie-breaker, a session reading another session's block, the
search cursor being ignored, an empty page marshalling as `null`, and raw truncation going
unreported. All six failed as intended.

## Deliberately not done

- **`origin` and `thread_id` filters are implemented but never exercised against real data**,
  because nothing creates agent blocks until T-F1-10.
- **`include: "raw"` returns at most 2 MiB.** A block may hold 16 MiB and base64 turns that
  into 21, five times the 4 MiB message limit of API Spec §8. The response says
  `output_raw_truncated`, which is honest but not a substitute for a paged chunk API; no F0
  client needs one.
- **No test stores 16 MiB**, so the raw cap is exercised at its boundary and not at scale.
- **Search ranking.** Results are ordered by recency, not relevance. `bm25` was measured at
  159 ms p95 and rejected on that alone; if relevance is wanted later it needs its own design,
  not a change of `ORDER BY`.
- **The benchmark corpus is generated, not committed.** The task file asked for
  `testdata/fixtures/blocks100k.sql.zst`; a 100,000-row binary is unreviewable, and a fixed
  seed gives the same corpus with the vocabulary readable in the test.
