## Evidence

- **REQ-SEC-013**: discard, keep the rules in force, "record the reason in `egress_log`", notify the user, "SHALL NOT retry that bundle".
- **REQ-SEC-014**: show the fingerprint, explicit confirmation, refuse the last valid key without `--force`, "record every change with its timestamp".
- **REQ-SEC-015**: no valid key or three consecutive failures disable updates until a manual `umb rules key add`.
- **REQ-SEC-016**: rollback and reset offline, without a key, never touching the local directory.
- **DD-016**: bundle and signature formats; a fetch that fails is not a failed verification; an unchanged bundle is up to date; the seed never reopens fail-closed.
- **Data Model §2.4e**: active and previous bundles kept; the active row's version is the floor.

## Decisions

1. **Migration `0006_rule_state`** (forward-only, Art. 6): `rule_bundles` gains `content BLOB`, the bundle's exact bytes, required for `remote` rows; `rule_rejections(sha256 PRIMARY KEY, reason, version, at)` remembers a bundle not to retry; `rule_update_state`, one row, holds `consecutive_failures`, the `fail_closed` latch, `ever_had_valid_key` (decision 4), `highest_version` (decision 2) and the last rejection; `trust_key_events(id, key_id, fingerprint, action, at)` records every trust-store change, a no-op add included, with `action` one of `seeded`, `seed_revoked`, `added`, `readded` (a revoked key added back), `unchanged` (an add of a key already valid) and `revoked`. A rotation records `added` and then `revoked`.
2. **Verification order and reasons.** A signature file that is not `{"signatures":[…]}` or holds no entry is `unsigned`; no entry naming a valid key is `unknown_key`; entries naming valid keys of which none checks out is `invalid_signature`; a verified bundle that is not a valid rule document (delta `2026-10-rule-overrides`, decision 1) or whose `version` is not positive is `invalid_bundle`; a `version` not above the floor is `downgrade`. The floor is the higher of the active row's version and `highest_version`, the highest version ever applied: a `rules.reset` makes version 0 active, and without the mark a compromised endpoint — DD-016's threat — could replay any older signed bundle to undo it. Only a revocation lowers the mark, to the highest version among the rows that survive it. Unverified bytes are never parsed, so a rejection before the signature checks out carries version 0 (NULL in `rule_rejections`). A bundle whose SHA-256 is the active one's is up to date and nothing happens. A bundle whose SHA-256 is in `rule_rejections` is skipped silently: not retried, not counted, not announced again. A `.sig` that cannot be fetched is a failed fetch, not `unsigned` (DD-016).
3. **What a rejection does.** In one transaction: the `rule_rejections` row, `rule_update_state`'s last rejection and its count, and an `egress_log` row `provider = 'umbral-rules:rejected:<reason>'` with the URL's host, the bundle's size as `bytes` and its digest — `egress_log` is the audit REQ-SEC-013 names, and a provider value carries the reason without a DDL change to an Art. 4 table. Then `rules.update_rejected {reason, version, source: "remote"}` is announced to every client, `umbral_rule_updates_rejected_total` counts it, and a user notification `Rule update rejected` naming the reason is raised through the notification sink under the daemon's own source `umbral:rules` (API §5.35) — REQ-SEC-013's "notify the user", since the broadcast alone reaches no person. `cmd/umbrald` subscribes to the event before the manager starts, so a rejection at the first check is not lost while the sink is built; the sink gains `ShowOwn`, the path for a source under the reserved prefix, which a client still cannot claim. The rules in force are not touched.
4. **Fail closed.** Three consecutive rejections set the latch; a bundle applied resets the count; a failed fetch or a skipped repeat neither counts nor resets. The trust store *ending up* without a valid key — a removal with `force` or a seed revocation taking the last one — sets the latch too. A store that has never held a valid key (`ever_had_valid_key` is 0) reports `disabled_fail_closed` without latching, so a fresh install picks up the first key a seed brings. Only a successful `rules.key.add` (or the add half of `rotate`) clears the latch, the seed never does. With the latch set, the fetcher makes no request.
5. **Applying.** A verified bundle is written as the active `remote` row with its bytes and `verified_with`, the former active row becomes inactive, and rows other than the active, the newest other `remote` (the previous bundle) and `builtin` are pruned — persisted before the rule set changes (DD-007). Then the active set's base is replaced by the bundle's rules, under the local layer (delta `2026-10-rule-overrides`, decision 2). At start the active row is loaded the same way; its bytes are checked against its digest and a mismatch falls back to the built-in rules with an error logged.
6. **Rollback and reset.** `rules.rollback` makes the previous bundle active and deletes the row it left, whose digest goes into `rule_rejections` as `rolled_back` so the next check does not reinstall it. `rules.reset` makes `builtin` active and records the former active digest as `reset`; the remote rows stay, so a later `rollback` reinstalls the newest and clears its record. Neither needs a key, the network or the latch to be clear, and neither counts as a rejection or is announced.
7. **The trust seed.** `internal/security/adapters/rules/trustseed/seed.json`, embedded: `{"keys":[{"id","public_key"}],"retired":["SHA256:…"],"revoked":["SHA256:…"]}`. It ships empty: the project key is created offline by the Tech Lead (`docs/runbooks/rule-signing.md` §4.1) and added by pull request. The `builtin` row's digest is the SHA-256 of the built-in rules' canonical JSON and is rewritten when it changes.
8. **The wire.** Keys are named by fingerprint. `rules.key.add {public_key, confirm_fingerprint}` and `rules.key.list {}` answer `{key}` and `{trust_keys}`; `rules.key.remove {fingerprint, force?}` answers `{key, active_bundle}`; `rules.key.rotate {fingerprint, public_key, confirm_fingerprint}` answers `{added, revoked, active_bundle}`; `rules.rollback {}` and `rules.reset {}` answer `rules.status`'s result. An unknown fingerprint is `NOT_FOUND`. Every client kind may call them, under the `rules` capability, and §2's `cli` row gains `rules.*`.
9. **The CLI.** `umb rules status`, `umb rules key list`, `umb rules key add PUBKEY --confirm SHA256:…`, `umb rules key remove FINGERPRINT [--force]`, `umb rules key rotate FINGERPRINT PUBKEY --confirm SHA256:…`, `umb rules rollback` and `umb rules reset`. Without `--confirm`, `add` and `rotate` print the key's fingerprint and exit 1 without calling the daemon: typing the fingerprint back is the explicit confirmation.
10. **`tools/rulesign`** is a Go command in this module, mapped in `.go-arch-lint.yml` to depend on `security-domain` only, so `verify` runs the daemon's own verification function.
11. **Accepted: rejections are keyed by the bundle's digest.** An endpoint serving the real next bundle with a bad `.sig` makes that bundle `invalid_signature` for good. REQ-SEC-013 forbids the retry, and the remedy is the project publishing the next version; keying by bundle and signature together would let an endpoint make the daemon re-verify one bundle without end.
