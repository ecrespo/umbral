## Build, test and lint

`AGENTS.md` above carries the full command table. What it does not cover:

| Purpose | Command |
|---|---|
| One package | `go test -race ./internal/store/...` |
| One test | `go test -race ./internal/api/ -run TestHelloRejectsBadToken_REQ_SEC_003 -v` |
| Every test covering one requirement | `go test -race ./... -run REQ_SEC_003` |
| Coverage (target ≥ 75 % in domain, policy and router) | `task test:cover` |
| NFR benchmarks, the whole picture | `task bench` |
| Only the benchmarks that gate, plus their selftest | `task perf` |

- **`task ci` is the gate, in the pipeline's own order:** specs, schema, icons, lint, arch,
  arch:selftest, test, perf, build. Run it before every commit; a green `go test` alone is not
  the gate. `task schema` is REQ-API-004's: it generates the protocol from the Go types and
  compares it with `specs/api/umbral-daemon-api-v1.md`, so a method or an error code that
  exists on one side and not the other fails the build.
- Test names carry their requirement id, so `-run REQ_XXX_NNN` is the fastest way to check
  one criterion. That naming is Art. 2, not a convention.
- `task tools:install` installs gofumpt, govulncheck, golangci-lint and go-arch-lint into
  `$(go env GOPATH)/bin`; that directory and the Go toolchain must be on `PATH` or every
  `task` target fails with "command not found". `gitleaks` is installed separately.
- `task specs` needs Python 3 and Node; it installs `tools/node_modules` on first run.

## Architecture

The daemon owns all state and the clients are thin: they render bytes and send input
(DD-001). Anything that survives closing a window lives in `umbrald`.

Inside the daemon the shape is a modular monolith with a hexagonal interior, and the
boundaries are **mechanically enforced**, not documented:

- Every module under `internal/` is split into `domain` (pure types, standard library
  only), `ports` (published interfaces) and `adapters` (implementations, external
  libraries). `.go-arch-lint.yml` writes out the Tech Design §5.2 rules component by
  component, with no implicit permissions, and `task arch` fails the build on a violation.
- `scripts/arch_selftest.sh` injects a forbidden `sessions` → `agents` import and asserts
  it is rejected. It exists because a misconfigured rules file passes silently; if you
  change `.go-arch-lint.yml`, this is what proves the change still bites.
- **`sessions` and `llmgw` may never import `agents`.** They communicate through
  `internal/bus`, a typed pub/sub. That constraint is the reason the bus exists at all.
- **`cmd/umbrald` is the only place allowed to wire modules together.** A module that
  reaches for another module's constructor is a boundary violation even if it compiles.

Three boundaries carry rules that are easy to break by accident:

- **`internal/api` is the only package that knows the wire format.** Modules return the
  sentinel errors in `internal/api/errors.go`; `toWire` maps them to JSON-RPC codes. A
  handler that returns a numeric code has leaked the protocol into the domain. Only
  `INTERNAL_ERROR` carries a trace id, and its message is replaced so internals never
  reach the client.
- **`internal/store` owns the schema, and the schema is the contract.** Pragmas travel in
  the DSN rather than as statements after connecting, because `database/sql` pools
  connections and a pragma issued once applies to one of them only. `Open` reads
  `foreign_keys` and `journal_mode` back instead of trusting the driver.
- **Persist before notifying** (DD-007): the agent runtime writes to SQLite in the turn's
  own goroutine before publishing on the bus.

Two things look like bugs and are not:

- **Migration 0001 creates `threads`**, an F1 table, because `sessions.owner_thread_id` and
  `blocks.thread_id` hold foreign keys against it and SQLite rejects every insert into a
  table whose foreign key points at a missing table, even with a NULL value. This was
  Analyze finding A-01; `TestMigration0001InsertsWithForeignKeysOn` is its regression test.
  Moving `threads` to the agent migration breaks all of F0.
- **The bus drops events under pressure** and counts the losses rather than blocking. A
  stalled TUI must never stall the goroutine draining a PTY. The client-facing backpressure
  policy, an 8 MiB queue that unsubscribes on overflow, belongs to the API fan-out in
  T-F0-06 and sits above this layer.

Identifiers are type-prefixed ULIDs generated by `store.NewID`, which lives in `store`
because the `CHECK` constraints that enforce those prefixes are in the migrations next
door. Timestamps are UTC epoch milliseconds and costs are `int64` micro-USD, everywhere,
including across the API (Art. 6).

## Claude Code specifics

- **Subagents** (`.claude/agents/`):
  - `spec-guardian`: read-only review against the constitution and the specs. Run it
    before every task commit. It reports findings and never edits or stages anything.
  - `test-author`: Go tests from the EARS criteria, using the exact names in the
    traceability matrix. Writes `_test.go` files only.
- **Not created yet**, although earlier notes described them: the project skills
  (`/implement-task`, `/spec-delta`, `/sdd-analyze`, `/checkpoint`), the session-start and
  post-edit hooks, `.claude/settings.json` with its permissions, and `.mcp.json`. Do not
  try to invoke them; create them first or work without them. Verified again on 2026-09-20:
  `.claude/` holds `agents/` and nothing else.
- **Migrations:** `0001_terminal`, `0002_block_index`, `0003_structure` and `0004_restore`
  are applied. `0005_agent` (T-F1-01) is not written yet. Migrations are forward-only
  (Art. 6), so an applied file is never edited; that is why the agent subdomain is `0004`
  and not the `0002` some older drafts name.
- **Recommended flow:** start each task in Plan Mode, get the plan approved, implement it,
  then run `spec-guardian` before writing the commit.
- **Before claiming a task is done**, verify against the filesystem rather than against
  your own notes. The checkpoints in `docs/checkpoints/` exist because earlier ones listed
  files that were never committed.
